1התמונה הגדולה

הפרויקט מורכב משני חלקים נפרדים שרצים במקביל ומדברים זה עם זה דרך HTTP:

צד לקוח (client): אפליקציית React

רץ בדפדפן. מציג את המסכים, מגיב ללחיצות, ושולח בקשות לשרת עם fetch. נבנה עם Vite (כלי שמריץ ובונה את קוד ה-React). זו אפליקציית עמוד יחיד (SPA): יש קובץ HTML אחד בלבד, client/index.html, ובו <div id="root"> ריק. React "מצייר" לתוכו את כל המסכים. מעבר בין "עמודים" לא טוען HTML חדש מהשרת. React Router רק מחליף את הקומפוננטה שמוצגת.

צד שרת (server): json-server

שרת מוכן שמקבל קובץ JSON, server/db.json, והופך אותו אוטומטית ל-REST API מלא. כל מפתח ראשי בקובץ (users, todos, posts, comments, albums, photos) הופך לכתובת (/users, /todos…) שאפשר לקרוא ממנה (GET), להוסיף אליה (POST), לעדכן בה (PATCH) ולמחוק ממנה (DELETE). כל שינוי נכתב חזרה לקובץ, ולכן הנתונים נשמרים גם אחרי שהשרת נסגר. המבנה זהה לזה של jsonplaceholder, כמו שהדרישות מבקשות.

React 19 React Router 7 Hooks: useState · useEffect · useReducer · Custom Hooks fetch + async/await json-server 0.17 LocalStorage Vite

כמה נתונים יש בשרת: 12 משתמשים, 186 משימות, 24 פוסטים ("מסלולים"), 57 תגובות, 31 אלבומים ו-300 תמונות. הקשרים ביניהם נשמרים בשדות מפתח זר:

users ──< todos      (todo.userId)
users ──< posts      (post.userId)   posts ──< comments (comment.postId)
users ──< albums     (album.userId)  albums ──< photos  (photo.albumId)

לכן כדי לקבל "את המשימות של משתמש 2" שולחים GET /todos?userId=2, והשרת מסנן בעצמו.

2איך מריצים

צריך שני טרמינלים, אחד לכל צד:

# טרמינל 1 – השרת (פורט 3001)
cd server
npm install
npm start          # = json-server --watch db.json --port 3001

# טרמינל 2 – הלקוח (בדרך כלל http://localhost:5173)
cd client
npm install
npm run dev
למה פורט 3001? כדי שלא יתנגש עם פורטים אחרים. הכתובת של השרת מוגדרת במקום אחד בלבד: BASE_URL בקובץ services/apiClient.jsx. --watch אומר לשרת לטעון את הקובץ מחדש אם משנים אותו ידנית.
טיפ להגנה פתחי את כלי המפתחים (F12) בלשונית Network והראי איך כל לחיצה שולחת בקשה. רואים שם את ה-Method, את הכתובת, את ה-Body שנשלח ואת התשובה. זו הדרך הכי טובה להוכיח שאת מבינה את התקשורת עם השרת.

3השכבות של הקוד ומבנה התיקיות

הקוד בצד הלקוח מחולק לשכבות. לכל שכבה יש תפקיד אחד, והיא מדברת רק עם השכבה שלידה. זה העיקרון החשוב ביותר להבין בפרויקט:

components/מה רואים. קומפוננטות React שמציגות את המסך ומגיבות למשתמש. הן לא יודעות איך מדברים עם השרת. הן רק קוראות לפונקציה מ-actions.
actions/מה עושים. פונקציות async שמתזמרות פעולה: קוראות לשרת דרך services, ואז מודיעות ל-reducer מה קרה בעזרת dispatch. כאן נמצא גם הטיפול בשגיאות (try/catch).
services/איך מדברים עם השרת. פונקציה לכל סוג בקשה (getTodos, createPost…). כולן עוברות דרך request אחת משותפת ב-apiClient, שהיא היחידה שקוראת ל-fetch.
reducers/איך ה-state משתנה. פונקציה טהורה שמקבלת state ישן ו-action ומחזירה state חדש. בלי fetch ובלי תופעות לוואי.
hooks/לוגיקה לשימוש חוזר. Custom Hooks: useSearch (חיפוש) ו-useSort (מיון). משותפים ל-Todos, ל-Posts ול-Albums.
styles/קובץ CSS נפרד לכל עמוד, כמו שהדרישות מבקשות. index.css מכיל את הסגנון הכללי (כפתורים, שדות וכו').

למה לפצל ככה ולא לכתוב הכול בקומפוננטה?

  • הפרדת אחריות: כל קובץ עושה דבר אחד. אם כתובת השרת משתנה, משנים שורה אחת ב-apiClient ולא 20 קומפוננטות.
  • שימוש חוזר: getTodos משמש גם את עמוד המשימות וגם את Home. useSearch משמש שלושה עמודים.
  • ה-reducer חייב להיות טהור: React דורש שה-reducer יחזיר תוצאה מיד, בלי לחכות לשרת. לכן כל מה שאסינכרוני (fetch) יושב ב-actions, וה-reducer רק מחשב.
  • כל פיצ'ר בנוי באותה תבנית: services → actions → reducer → עמוד → פריט. מי שמבין את Todos מבין גם את Posts ואת Albums.

4מסע של בקשה: מלחיצה, לשרת, ובחזרה למסך

זו השאלה שהכי סביר שתישאל. נעקוב אחרי דוגמה אחת מלאה: המשתמשת מסמנת V על משימה. הצבע של כל שלב מראה את השכבה שבה הוא קורה.

  1. ToDoItem.jsx המשתמשת לוחצת על ה-checkbox. ל-ToDoItem אין גישה לשרת ולא ל-state של הרשימה. הוא רק מפעיל את הפונקציה שקיבל מאבא שלו ב-props: 
    <input type="checkbox" checked={todo.completed} onChange={onToggle} />
  2. ToDos.jsx האבא (Todos) הגדיר מה onToggle עושה. כשהוא יצר את הפריט, הוא העביר לו פונקציה שקוראת ל-action עם ה-dispatch שלו: 
    <TodoItem
  todo={todo}
  onToggle={() => updateTodo(dispatch, todo.id, { completed: !todo.completed })}
/>
  3. todosActions.jsx ה-action קורא לשירות ומחכה לתשובה. 
    export async function updateTodo(dispatch, id, changes) {
  try {
    const updated = await patchTodo(id, changes);   // ⏸ מחכה לשרת
    dispatch({ type: "UPDATE", payload: updated });
  } catch {
    dispatch({ type: "SET_ERROR", payload: "עדכון המשימה נכשל" });
  }
}
  4. todosApi.jsx השירות יודע איזו כתובת ואיזה Method. 
    export function patchTodo(id, changes) {
  return request(`/todos/${id}`, { method: "PATCH", body: changes });
}
  5. apiClient.jsx request בונה את הבקשה ושולחת אותה עם fetch. האובייקט הופך למחרוזת JSON, ומוסיפים כותרת שאומרת לשרת שזה JSON: 
    const options = { method: "PATCH",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ completed: true }) };

const res = await fetch("http://localhost:3001/todos/21", options);
if (!res.ok) throw new Error(`שגיאת שרת (${res.status})`);
return res.json();
  6. json-server השרת מקבל, מעדכן את db.json ועונה. הוא מוצא את המשימה עם id: 21, ממזג לתוכה רק את completed (זה ההבדל בין PATCH ל-PUT), שומר לקובץ ומחזיר את המשימה המעודכנת כולה עם סטטוס 200 OK: 
    { "userId": 2, "id": 21, "title": "...", "completed": true }
  7. apiClient.jsx התשובה חוזרת. res.ok נכון (סטטוס 200–299), ולכן res.json() הופך את הטקסט לאובייקט JS. ה-Promise מתממש, וה-await ב-action ממשיך.
  8. todosActions.jsx ה-action מודיע ל-reducer מה קרה. 
    dispatch({ type: "UPDATE", payload: { id: 21, completed: true, ... } });
  9. todoReducer.jsx ה-reducer מחשב state חדש. הוא לא משנה את המערך הקיים. הוא יוצר מערך חדש שבו המשימה הישנה מוחלפת בזו שהשרת החזיר: 
    case "UPDATE":
  return { ...state,
    todos: state.todos.map(t => t.id === action.payload.id ? action.payload : t) };
  10. React React מזהה state חדש ומרנדר מחדש. Todos רץ שוב עם state.todos החדש. useSearch ו-useSort מחשבים מחדש את הרשימה המסוננת והממוינת. ToDoItem של משימה 21 מקבל todo.completed === true, וה-V מופיע.
המשפט לזכור הנתונים יורדים מלמעלה למטה דרך props (Todos → ToDoItem). האירועים עולים מלמטה למעלה דרך פונקציות callback (ToDoItem → onToggle → Todos). Todos מעביר את הבקשה לשרת דרך actions ו-services, והתשובה חוזרת ל-state דרך dispatch ו-reducer.
למה מעדכנים את ה-state רק אחרי שהשרת ענה? כך המסך מציג תמיד את מה שבאמת שמור בשרת. אם השרת נכשל, ה-state לא משתנה ומוצגת הודעת שגיאה. בנוסף, ב-POST השרת הוא זה שמייצר את ה-id, ולכן חייבים את התשובה שלו כדי להוסיף את הפריט החדש לרשימה.

איך נראית טעינה ראשונה של רשימה

כשנכנסים לעמוד, ה-useEffect מפעיל את loadTodos. הוא שולח שלוש הודעות ל-reducer לאורך הדרך, וכך המסך יודע מתי להציג "טוען...":

useEffect(() => { loadTodos(dispatch, userId); }, [userId]);

loadTodos:
  dispatch({ type: "LOAD_START" })                → loading: true   → "טוען..."
  const data = await getTodos(userId)              → GET /todos?userId=2
  dispatch({ type: "LOAD_SUCCESS", payload: data }) → loading: false, todos: data → הרשימה
  (אם נכשל) dispatch({ type: "SET_ERROR", ... })    → loading: false, error: "..." → הודעה אדומה

5ניתוב (React Router)

ב-main.jsx כל האפליקציה עטופה ב-<BrowserRouter>. זה מה שמאפשר להשתמש בכל ה-Hooks של הניתוב. ב-App.jsx נמצאת "טבלת הניתוב":

<Routes>
  <Route path="/"                 element={<Navigate to="/login" replace />} />
  <Route path="/login"            element={<Login />} />
  <Route path="/register"         element={<Register />} />
  <Route path="/register/details" element={<CompleteDetails />} />

  <Route path="/users/:username" element={<Layout />}>      ← נתיב אב
    <Route index                    element={<Home />} />    ← /users/Bret
    <Route path="todos"             element={<Todos />} />   ← /users/Bret/todos
    <Route path="posts/:postId?"    element={<Posts />} />   ← /users/Bret/posts/7
    <Route path="albums"            element={<Albums />} />
    <Route path="albums/:albumId/photos" element={<Photos />} />
  </Route>

  <Route path="*" element={...} />                         ← כל כתובת אחרת: "לא נמצא"
</Routes>

נתיבים מקוננים (Nested Routes) ו-Outlet

כל עמודי היישום הם ילדים של /users/:username. לכן React Router מציג קודם את Layout (הכותרת עם שם המשתמש ו-5 הכפתורים), ובמקום שבו Layout שם <Outlet /> הוא מציג את הילד המתאים לכתובת. הכותרת נכתבת פעם אחת ולא בכל עמוד. כשעוברים בין Todos ל-Posts, Layout נשאר ורק התוכן של ה-Outlet מתחלף.

קישורים יחסיים ב-Layout כתוב to="todos" ולא to="/users/Bret/todos". בלי / בהתחלה הקישור יחסי לנתיב הנוכחי, כך שהוא עובד לכל משתמש. ב-Photos, to="../.." עם relative="path" עולה שני חלקים בכתובת: מ-albums/5/photos ל-albums.
מה זה replace? navigate(url, { replace: true }) מחליף את הכתובת הנוכחית בהיסטוריה במקום להוסיף כתובת חדשה. אחרי Login משתמשים ב-replace כדי שכפתור "חזור" בדפדפן לא יחזיר לטופס הכניסה.

6איך נתונים עוברים בין קומפוננטות

בפרויקט יש שש דרכים שבהן מידע עובר ממקום למקום. כדאי להכיר כל אחת ולדעת למה בחרנו בה:

עץ הקומפוננטות

BrowserRouter └─ App (Routes) ├─ Login ──navigate──▶ /users/:username ├─ Register ──navigate + state {username,password}──▶ CompleteDetails └─ Layout (reads user from localStorage) ├─ Info props: user, onClose └─ Outlet context={{ user }} ├─ Home ├─ Todos useReducer → state.todos │ ├─ TodoSort props: sortBy, onSortChange │ └─ TodoItem ×N props: todo, onToggle, onEdit, onDelete ├─ Posts useReducer → state.posts · URL → postId, all │ ├─ PostItem ×N props: post, isSelected, onSelect │ ├─ PostForm props: submitLabel, onSubmit, onCancel │ └─ PostDetails props: post, isMine, onEdit, onDelete │ ├─ PostForm props: initialPost, ... │ └─ Comments props: postId useReducer → state.comments │ └─ CommentItem ×N props: comment, isMine, onEdit, onDelete ├─ Albums useReducer → state.albums │ └─ AlbumItem ×N props: album, onDelete └─ Photos useReducer → state.photos · URL → albumId └─ PhotoItem ×N props: photo, onEdit, onDelete

1. Props: מאבא לילד

הדרך הבסיסית. האבא מחזיק את הנתונים (ה-state) ומעביר לכל ילד רק את מה שהוא צריך. דוגמה: Posts מחזיק את כל הפוסטים ומעביר לכל PostItem פוסט אחד. הילד לא יכול לשנות props. הם לקריאה בלבד.

2. פונקציות callback: מילד לאבא

כשילד צריך לשנות משהו, האבא מעביר לו פונקציה כ-prop, והילד קורא לה. דוגמה: CommentItem מקבל onDelete. כשלוחצים "מחיקה" הוא קורא ל-onDelete(), והפונקציה, שהוגדרה ב-Comments, מבצעת deleteComment(dispatch, comment.id). כך ה-state נשאר במקום אחד ("Single Source of Truth"), והילדים נשארים פשוטים וניתנים לשימוש חוזר.

למה שימוש חוזר? PostForm משמש גם להוספה (ב-Posts) וגם לעדכון (ב-PostDetails). הוא לא יודע מה יקרה בשליחה. הוא רק קורא ל-onSubmit(title, body), וכל אבא מחליט בעצמו מה לעשות עם זה.

3. Outlet Context: המשתמש המחובר לכל העמודים

כל העמודים צריכים לדעת מי המשתמש המחובר. במקום שכל אחד יקרא בעצמו מ-localStorage, Layout קורא פעם אחת ומעביר:

// Layout.jsx
<Outlet context={{ user }} />

// Todos.jsx / Posts.jsx / Albums.jsx / Photos.jsx / Home.jsx / Comments.jsx
const { user } = useOutletContext();

זה עובד בכל קומפוננטה שנמצאת בתוך ה-Outlet, גם עמוק בעץ. Comments, למשל, נמצא שלוש רמות מתחת ל-Posts, ובכל זאת מקבל את user בלי להעביר אותו דרך כל הרמות ("prop drilling").

4. הכתובת (URL): מצב שצריך לשרוד רענון

ב-Posts, איזה פוסט נבחר והאם מציגים את כל הפוסטים לא נשמרים ב-useState. הם נשמרים בכתובת (useParams ו-useSearchParams). כך רענון (F5) לא מוחק את הבחירה, כפתור "חזור" עובד, והכתובת מתארת את המצב. זה עונה על הדרישה לכתובת אינפורמטיבית ועל האתגר של שרידות לרענון. ב-Photos, ה-albumId מגיע מהכתובת באותו אופן.

5. navigate עם state: בין שני מסכים לא קשורים

בהרשמה יש שני מסכים: Register (שם משתמש וסיסמה) ו-CompleteDetails (פרטים). הם לא אבא וילד, ולכן אי אפשר להעביר props. המשתמש עוד לא נשמר בשרת, ולא רצינו לשמור סיסמה ב-localStorage. הפתרון הוא לשלוח את הנתונים יחד עם המעבר:

// Register.jsx
navigate("/register/details", { state: { username, password } });

// CompleteDetails.jsx
const registerData = useLocation().state;   // { username, password } או null
if (!registerData) return <Navigate to="/register" replace />;   // הגיעו ישירות בלי הרשמה

6. LocalStorage: מי מחובר, גם אחרי רענון

ב-Login וב-CompleteDetails שומרים את המשתמש (בלי הסיסמה) תחת המפתח "currentUser". LocalStorage שומר רק מחרוזות, ולכן משתמשים ב-JSON.stringify בשמירה וב-JSON.parse בקריאה. Layout קורא משם בכל רינדור. אם אין משתמש, הוא מפנה ל-/login. Logout מוחק את המפתח. בגלל זה רענון הדף לא מנתק את המשתמש.

ומה כל קומפוננטה מחזיקה בעצמה? (state מקומי)

state שרק קומפוננטה אחת צריכה נשאר אצלה. למשל isEditing ו-newTitle ב-ToDoItem: רק הפריט עצמו צריך לדעת שהוא במצב עריכה. showComments ב-PostDetails ו-showInfo ב-Layout עובדים באותו אופן. הכלל הוא לשמור state כמה שיותר נמוך בעץ, ולהעלות אותו רק כשכמה קומפוננטות צריכות אותו (Lifting State Up).

7כל עמוד: מה הוא עושה ואיך

Login: כניסה components/Login.jsx

  1. שני שדות נשלטים (controlled): value={username} + onChange → setUsername.
  2. בשליחה: e.preventDefault() (בלי זה הדפדפן היה שולח את הטופס ומרענן את הדף), ובדיקה שהשדות לא ריקים.
  3. GET /users?username=Bret. השרת מחזיר מערך: ריק אם המשתמש לא קיים, או עם משתמש אחד אם קיים.
  4. אם אין משתמש או שהסיסמה (השדה password שהוספנו ל-db.json) לא תואמת, מוצגת שגיאה ונשארים בעמוד.
  5. אם הכול תקין: עותק של המשתמש בלי סיסמה נשמר ב-localStorage, ומתבצע navigate(`/users/${user.username}`, { replace: true }).
  6. אם fetch נכשל (השרת לא רץ), ה-catch מציג "אין חיבור לשרת".

Register + CompleteDetails: הרשמה

  1. Register: שלושה שדות. בדיקות בצד הלקוח: שדות ריקים, שם משתמש "בטוח לכתובת", ושתי הסיסמאות זהות.
  2. שם משתמש בטוח לכתובת: השם הופך לחלק מהכתובת (/users/<username>), ולכן הוא נבדק מול ביטוי רגולרי: 
    const USERNAME_PATTERN = /^[A-Za-z][A-Za-z0-9._-]{2,19}$/;
    מתחיל באות באנגלית, ואחריה רק אותיות באנגלית, ספרות, ., _ או -. סך הכול 3 עד 20 תווים. בלי הבדיקה הזו:
    • a/todos: ה-/ מפצל את הכתובת. React Router קורא username = "a", ו-Layout רואה ש-"a" שונה מ-"a/todos" ומפנה שוב לאותה כתובת. התוצאה היא לולאת הפניות אינסופית.
    • a/b: אין נתיב b, ולכן המשתמש מגיע ל"העמוד לא נמצא" ולא יכול להיכנס לעולם.
    • a?b או a#b: ? מתחיל query ו-# מתחיל עוגן, כך שהשם "נחתך". שוב יש אי-התאמה ולולאה.
    • ..: הדפדפן מפרש אותו כ"תיקייה אחת למעלה", כלומר /users/.. הופך ל-/.
    ומה עם שם כמו login? הוא מותר ולא מתנגש, כי כל עמודי המשתמש נמצאים תחת הקידומת /users/. הכתובת היא /users/login ולא /login. זו בדיוק הסיבה שבחרנו בקידומת.
  3. אותה בקשה כמו ב-Login, GET /users?username=..., אבל עם היגיון הפוך: מערך לא ריק אומר שהשם תפוס.
  4. אם השם פנוי: navigate ל-/register/details עם state (ראו סעיף 6.5).
  5. CompleteDetails: כל ארבעת השדות ב-state אחד (אובייקט). פונקציה אחת מטפלת בכל השדות לפי ה-name של ה-input: 
    const handleChange = (e) => {
  const { name, value } = e.target;
  setDetails({ ...details, [name]: value });   // [name] = מפתח דינמי
};
  6. POST /users עם המשתמש החדש. השרת מוסיף לו id ומחזיר אותו. אחר כך נשמר ב-localStorage, בדיוק כמו ב-Login, ומתבצע מעבר לעמוד היישום.

Layout + Info + Logout + Home: המסגרת

  • שמירה על העמודים (הגנה): אם אין משתמש ב-localStorage, הפניה ל-login. אם ה-:username בכתובת שונה מהמשתמש המחובר (ניסיון להיכנס לנתונים של מישהו אחר), הפניה לכתובת של המשתמש המחובר. זה האתגר של מניעת גישה לנתונים של משתמש אחר.
  • כותרת עם השם המלא, ו-5 כפתורים: Info, Todos, Posts, Albums, Logout.
  • Info מוצג כחלון צף (overlay). לחיצה על הרקע סוגרת, ו-e.stopPropagation() בתוך החלון מונע מלחיצה בפנים "לבעבע" לרקע ולסגור אותו.
  • Home שולח שלוש בקשות במקביל עם Promise.all ומחכה לכולן יחד, כדי להציג מונים בכרטיסים.

Todos: משימות components/todos/

  • useReducer(todosReducer, initialTodosState) מחזיק { todos, loading, error }.
  • הצגה: id, כותרת ו-checkbox של completed, לכל משימה.
  • חיפוש: useSearch(state.todos, ["title","id","completed"]). בכותרת מספיק שהטקסט מוכל בה. ב-id וב-completed נדרשת התאמה מדויקת. בחיפוש לפי ביצוע מוצג select עם הערכים "true" ו-"false".
  • מיון: useSort(filtered, "id"). קודם מסננים ואז ממיינים. compareValues מטפל בבוליאני (false לפני true), במספרים (השוואה מספרית, כדי ש-"10" לא יבוא לפני "9") ובטקסט (localeCompare בעברית).
  • הוספה: POST /todos עם completed: false. עדכון תוכן: ToDoItem נכנס למצב עריכה מקומי (Enter שומר, Escape מבטל) ושולח PATCH { title }. עדכון מצב: PATCH { completed }. מחיקה: DELETE.

Posts + Comments: מסלולים ותגובות components/posts/

  • שלי / כולם: שני כפתורים שמשנים את ?all=true בכתובת. ה-useEffect תלוי ב-showAll, ולכן כל החלפה טוענת מחדש: GET /posts?userId=2 או GET /posts. ה-effect משתמש בדגל ignore, כדי שתשובה ישנה לא תדרוס את הרשימה אחרי מעבר מהיר בין המצבים (ראו סעיף 8, useEffect).
  • סקירה: PostItem מציג רק id וכותרת, כמו שהדרישות מבקשות.
  • בחירה: לחיצה על "בחירה" מבצעת navigate ל-posts/7. הפוסט הנבחר מחושב מהרשימה (state.posts.find(...)) ולא נשמר כעותק נפרד ב-state. הפריט מקבל class selected (הדגשה), ו-PostDetails מציג את ה-body.
  • הרשאות: isMine = String(post.userId) === String(user.id). כפתורי עדכון ומחיקה מוצגים רק לפוסטים של המשתמש המחובר.
  • הוספה: addPost מחזיר את הפוסט החדש מהשרת, ו-Posts מנווט אליו מיד כדי שייבחר.
  • עדכון: PostForm נפתח עם הנתונים הקיימים, ונשלח רק מה שהשתנה (PATCH).
  • מחיקה: window.confirm ואז DELETE /posts/7. json-server מוחק אוטומטית גם את כל התגובות עם postId: 7 (מחיקה מדורגת).
  • תגובות: נטענות רק בלחיצה על "הצג תגובות", כי Comments נוצר רק אז. לכל תגובה נשמרים userId (לזיהוי הכותב ולהרשאות) ו-name (לתצוגה). מותר להגיב לכל פוסט, אבל עדכון ומחיקה מותרים רק לתגובות שלי (isMine).
  • key={selectedPost.id} על PostDetails: כשעוברים לפוסט אחר, React יוצר קומפוננטה חדשה. זה מאפס את ה-state הפנימי שלה, כך שמצב עריכה או תגובות פתוחות לא "נגררים" לפוסט הבא.

Albums + Photos: אלבומים ותמונות components/albums/ · photos/

  • Albums: GET /albums?userId=2. כל כרטיס מציג רק id וכותרת, יש חיפוש לפי id או כותרת, יצירה (POST) ומחיקה (DELETE, שמוחק גם את התמונות של האלבום).
  • תמונת כריכה: כל AlbumItem מבקש תמונה אחת בלבד, _limit=1, ולא את כל התמונות.
  • קישור לתמונות: <Link to={`${album.id}/photos`}> מוביל ל-/users/Bret/albums/5/photos.
  • בדיקת בעלות: Photos מביא את האלבום (GET /albums/5) ובודק ש-album.userId שווה למשתמש המחובר. אחרת מוצג "האלבום לא נמצא". כך אי אפשר להקליד כתובת של אלבום של מישהו אחר.
  • טעינה בשלבים (דרישה מפורשת: לא להביא את כל התמונות בבת אחת): 
    GET /photos?albumId=5&_start=0&_limit=4    ← טעינה ראשונה
GET /photos?albumId=5&_start=4&_limit=4    ← "הצג עוד"
GET /photos?albumId=5&_start=8&_limit=4    ← "הצג עוד"
    _start ו-_limit הם פרמטרים מובנים של json-server. ב-LOAD_MORE_SUCCESS ה-reducer מוסיף לסוף הרשימה ולא מחליף אותה. hasMore הוא true כל עוד חזרו בדיוק 4 תמונות. כשחוזרות פחות, אין יותר תמונות והכפתור נעלם.
  • למה addedIds? תמונה שהוספנו נשמרת בשרת בסוף הרשימה. אם היינו סופרים אותה ב-_start, היינו מדלגים על תמונה מהשרת. לכן start = photos.length - addedIds.length, וה-reducer מסנן כפילויות לפי id.
  • ניהול תמונות: הוספה (כותרת ו-URL), עדכון (כותרת ו/או URL, נשלח רק מה שהשתנה) ומחיקה.

8מילון מושגים, ואיפה כל אחד מופיע בפרויקט

יסודות React

קומפוננטה (Component)

פונקציה שמחזירה JSX, כלומר תיאור של מה להציג. שם שמתחיל באות גדולה. כל קובץ ב-components/ מכיל קומפוננטה. React קורא לפונקציה שוב (רינדור) בכל פעם שה-state או ה-props שלה משתנים.

JSX

תחביר שנראה כמו HTML בתוך JavaScript. Vite מתרגם אותו לקריאות JS. ההבדלים מ-HTML: className במקום class, ביטויי JS בתוך { }, ו-onClick עם פונקציה ולא עם מחרוזת.

Props

הפרמטרים של קומפוננטה, שעוברים מאבא לילד. לקריאה בלבד. דוגמה: <PostItem post={post} isSelected={...} onSelect={...} />.

State ו-useState

"זיכרון" של קומפוננטה, שנשמר בין רינדורים. const [value, setValue] = useState(initial). קריאה ל-setValue גורמת לרינדור מחדש. משתנה רגיל (let) לא היה גורם לרינדור, והיה מתאפס בכל קריאה לפונקציה. בפרויקט: שדות טפסים, error, isEditing, showInfo, isAdding.

Immutability: לא משנים state ישירות

React משווה את ה-state הישן לחדש לפי הפניה. אם משנים את אותו מערך (todos.push(x)), ההפניה לא משתנה, ו-React לא יודע שצריך לרנדר. לכן תמיד יוצרים עותק חדש:

[...state.todos, newTodo]                          // הוספה
state.todos.filter(t => t.id !== id)              // מחיקה
state.todos.map(t => t.id === id ? updated : t)    // עדכון
{ ...state, loading: true }                       // שינוי שדה באובייקט

Controlled Components: טפסים נשלטים

שדה שהערך שלו מגיע מ-state (value={title}), וכל הקלדה מעדכנת את ה-state (onChange). כך ה-state הוא מקור האמת, ואפשר לבדוק, לנקות (setNewTitle("") אחרי הוספה) ולמלא מראש (בעריכה). כל הטפסים בפרויקט בנויים כך.

e.preventDefault()

ברירת המחדל של טופס HTML בשליחה היא לטעון את הדף מחדש. ב-SPA זה היה מוחק את כל ה-state. לכן כל onSubmit מתחיל ב-e.preventDefault().

רינדור מותנה

{error && <p>{error}</p>}                  // מוצג רק אם יש שגיאה
{isEditing ? <input .../> : <span>...</span>}   // אחד משניים
if (state.loading) return <p>טוען...</p>;     // return מוקדם

רשימות ו-key

מציגים רשימה עם .map(). כל פריט חייב key ייחודי ויציב (בפרויקט: key={todo.id}). React משתמש ב-key כדי לדעת איזה פריט נוסף, נמחק או זז, ובכך לשמור את ה-state הנכון לכל פריט. לא משתמשים באינדקס כ-key, כי אחרי מחיקה או מיון האינדקסים זזים. key משמש גם לאיפוס מכוון: key={selectedPost.id}.

Derived State: נתון מחושב, לא שמור

מה שאפשר לחשב מ-state קיים לא שומרים ב-state נוסף. filtered (ב-useSearch), sorted (ב-useSort), selectedPost ו-isMine מחושבים מחדש בכל רינדור. כך אין סכנה ששני מקורות יפסיקו להיות מתואמים.

Hooks

useEffect

מריץ קוד אחרי שהקומפוננטה הוצגה. הוא מיועד ל"תופעות לוואי" כמו פנייה לשרת. מערך התלויות קובע מתי הוא רץ שוב:

useEffect(() => { loadTodos(dispatch, userId); }, [userId]);
// [] – פעם אחת בטעינה · [userId] – בטעינה ובכל פעם ש-userId משתנה

ב-Posts התלות היא [userId, showAll], ולכן מעבר בין "שלי" ל"כולם" טוען מחדש. ב-Photos התלות היא [albumId].

פונקציית ניקוי ודגל ignore (ב-Home, AlbumItem, Photos ו-Posts): אם יוצאים מהעמוד, או שה-effect רץ שוב עם ערך חדש לפני שהתשובה הקודמת הגיעה, ה-cleanup מסמן ignore = true, והתשובה הישנה לא תעדכן state. זה מונע Race Condition, מצב שבו תשובה ישנה דורסת חדשה.

useEffect(() => {
  let ignore = false;
  getAlbum(albumId).then(data => { if (!ignore) setAlbum(data); });
  return () => { ignore = true; };     // רץ לפני ה-effect הבא / ביציאה
}, [albumId]);

הדוגמה ב-Posts. מעבר מהיר בין "כל המסלולים" ל"המסלולים שלי" שולח שתי בקשות במקביל. אם הבקשה הראשונה (GET /posts, הגדולה והאיטית יותר) חוזרת אחרי השנייה, היא דורסת את הרשימה, ומוצגים הפוסטים של כולם כשהכפתור "שלי" מסומן. כאן ה-effect לא קורא ל-setState בעצמו, אלא מעביר את dispatch ל-action. לכן עוטפים את dispatch בפונקציה שבודקת את הדגל, בלי לשנות את loadPosts:

useEffect(() => {
  let ignore = false;
  const safeDispatch = (action) => {
    if (!ignore) dispatch(action);     // תשובה ישנה – לא מגיעה ל-reducer
  };
  loadPosts(safeDispatch, userId, showAll);
  return () => { ignore = true; };
}, [userId, showAll]);

למה אין ignore ב-Todos, Albums ו-Comments? ב-Todos וב-Albums התלות היא רק userId, והוא לא משתנה בזמן שנמצאים בעמוד, כך שאין שתי בקשות שמתחרות. ב-Comments, ל-PostDetails יש key={post.id}, ולכן מעבר לפוסט אחר יוצר רכיב Comments חדש, ו-dispatch לרכיב הישן כבר לא משפיע על המסך.

useReducer

חלופה ל-useState כשה-state מורכב ויש לו כמה סוגי שינויים. במקום הרבה setX מפוזרים, שולחים action (אובייקט עם type ו-payload), ופונקציה אחת, ה-reducer, מחליטה איך ה-state משתנה.

const [state, dispatch] = useReducer(todosReducer, initialTodosState);
dispatch({ type: "DELETE", payload: 21 });
// React קורא: todosReducer(stateהנוכחי, {type:"DELETE", payload:21}) → state חדש

למה בפרויקט? לכל רשימה יש אותם 6 מצבים (טעינה, הצלחה, שגיאה, הוספה, עדכון, מחיקה). כל הלוגיקה מרוכזת במקום אחד וקריאה. ה-reducer חייב להיות פונקציה טהורה: אותו קלט נותן אותו פלט, בלי fetch ובלי שינוי של ה-state הקיים. בגלל זה הקריאות לשרת נמצאות ב-actions.

Custom Hooks: useSearch, useSort

פונקציה ששמה מתחיל ב-use ומשתמשת בתוכה ב-Hooks אחרים. היא מאפשרת לשתף לוגיקה עם state בין קומפוננטות. כל קומפוננטה שקוראת ל-useSearch מקבלת state משלה (query, searchBy), לא state משותף. useSearch מקבל רשימה ושדות ומחזיר { query, setQuery, searchBy, setSearchBy, filtered }.

חוקי ה-Hooks

קוראים ל-Hooks רק ברמה העליונה של קומפוננטה: לא בתוך if, לא בתוך לולאה, ולא אחרי return מוקדם. React מזהה כל Hook לפי הסדר שבו הוא נקרא. לכן ב-Todos, ב-Posts וב-CompleteDetails כל ה-Hooks נמצאים לפני if (state.loading) return .... ההערות בקוד מציינות את זה במפורש.

StrictMode

ב-main.jsx האפליקציה עטופה ב-<StrictMode>. במצב פיתוח בלבד, React מריץ כל effect פעמיים כדי לחשוף באגים (למשל effect בלי ניקוי). לכן ב-Network רואים כל GET פעמיים. בגרסת production זה לא קורה.

JavaScript אסינכרוני ותקשורת

Promise, async ו-await

פנייה לשרת לוקחת זמן. fetch מחזיר מיד Promise, "הבטחה" לתשובה עתידית. await עוצר את הפונקציה (רק אותה, לא את הדפדפן) עד שה-Promise מתממש. מותר להשתמש ב-await רק בתוך פונקציה async. פונקציה async תמיד מחזירה Promise בעצמה. שגיאות נתפסות עם try/catch. ב-Home משתמשים ב-Promise.all, שמריץ שלוש בקשות במקביל ומחכה לכולן.

fetch

פונקציה מובנית בדפדפן לשליחת בקשות HTTP. שתי נקודות חשובות שמטופלות ב-apiClient:

  • fetch לא נכשל בסטטוס 404 או 500. הוא נכשל רק אם אין חיבור בכלל. לכן בודקים res.ok וזורקים שגיאה ידנית.
  • התשובה מגיעה כטקסט. res.json() (גם הוא Promise) הופך אותה לאובייקט. בשליחה עושים את ההפך: JSON.stringify(body), עם הכותרת Content-Type: application/json.

REST הוא סגנון לבניית API: כל משאב מקבל כתובת (/todos, /todos/21), וה-Method אומר מה עושים בו:

Query String: הפילטרים של json-server

  • ?userId=2: סינון לפי שדה. השרת מחזיר רק פריטים שבהם userId הוא 2.

CORS

הלקוח רץ על פורט 5173 והשרת על 3001. מבחינת הדפדפן אלה שני "מקורות" שונים, ובדרך כלל הוא חוסם בקשות ביניהם. json-server מוסיף כברירת מחדל את הכותרות שמתירות את זה, ולכן זה עובד בלי הגדרה נוספת.

LocalStorage

אחסון בדפדפן שנשמר גם אחרי רענון וסגירה. פועל לפי מפתח וערך, והערך הוא מחרוזת בלבד. ה-API: setItem, getItem ו-removeItem. ב-Layout הקריאה עטופה ב-try/catch, למקרה שהערך שם פגום ו-JSON.parse נכשל.

SPA ו-Vite

SPA (Single Page Application): דף HTML אחד. JavaScript מחליף את התוכן, וההחלפה מהירה בלי טעינה מחדש. Vite הוא שרת הפיתוח וכלי הבנייה. הוא מתרגם JSX, מאחד את הקבצים, ומרענן את הדפדפן אוטומטית כששומרים קובץ.

11שאלות צפויות בהגנה, עם תשובות

תארי את הדרך של בקשה מהלחיצה ועד שהמסך מתעדכן.
לחיצה בקומפוננטת פריט מפעילה callback שהגיע מה-props. האבא קורא ל-action עם dispatch. ה-action קורא לפונקציה ב-services. הפונקציה קוראת ל-request, ו-request שולח fetch לשרת עם Method, כתובת ו-body ב-JSON. json-server מעדכן את db.json ומחזיר JSON. res.json() מחזיר את התשובה ל-action, וה-action מבצע dispatch({type, payload}). ה-reducer מחזיר state חדש, ו-React מרנדר מחדש. (פירוט מלא בסעיף 4.)
למה יש גם actions וגם reducer? למה לא לעשות fetch בתוך ה-reducer?
ה-reducer חייב להיות פונקציה טהורה וסינכרונית. React קורא לו ומצפה לקבל state מיד, ולפעמים אפילו קורא לו פעמיים. fetch הוא אסינכרוני ובעל תופעת לוואי. לכן ה-action מטפל בצד האסינכרוני (שרת, try/catch), ורק כשיש תוצאה הוא שולח אותה ל-reducer. ה-reducer רק מחשב.
מה ההבדל בין useState ל-useReducer, ולמה השתמשתם בכל אחד?
useState מתאים לערך פשוט עם שינוי פשוט, כמו שדה טופס, isEditing או showInfo. useReducer מתאים ל-state מורכב (todos + loading + error) עם כמה סוגי שינויים. כל המעברים מוגדרים במקום אחד, ואותה תבנית חוזרת בכל הפיצ'רים.
איך המשתמש המחובר מגיע לכל העמודים?
Login שומר אותו ב-localStorage. Layout קורא אותו משם ומעביר אותו ב-<Outlet context={{ user }} />. כל עמוד, וכל קומפוננטה בתוך ה-Outlet, מקבלים אותו עם useOutletContext(). כך אין צורך להעביר אותו ב-props דרך כל הרמות.
מה קורה כשמרעננים את הדף (F5)?
כל ה-state של React נמחק. המשתמש נשמר, כי Layout קורא אותו מחדש מ-localStorage. העמוד הנוכחי נשמר, כי React Router קורא את הכתובת ומציג את הקומפוננטה המתאימה. הפוסט הנבחר ומצב "שלי / כולם" נשמרים, כי הם בכתובת. הרשימות עצמן נטענות מחדש מהשרת ב-useEffect.
מה קורה אם מקלידים בכתובת /users/Antonette כשמחוברת כ-Bret?
Layout משווה את useParams().username ל-user.username מ-localStorage. הם שונים, ולכן הוא מחזיר <Navigate to="/users/Bret" replace />. אם אף אחד לא מחובר, הוא מפנה ל-/login. לגבי אלבום של משתמש אחר: Photos מביא את האלבום ובודק את userId שלו.
למה useEffect ולא פשוט לקרוא ל-loadTodos בגוף הקומפוננטה?
גוף הקומפוננטה רץ בכל רינדור. קריאה לשרת שם הייתה מעדכנת state, מה שגורם לרינדור, שגורם לעוד קריאה, וכך בלולאה אינסופית. useEffect רץ אחרי הרינדור, ולפי מערך התלויות: רק כש-userId משתנה.
מה זה הדגל ignore, ולמה הוא נמצא ב-Posts?
הדגל מונע Race Condition: מצב שבו שתי בקשות יצאו, והתשובה של הישנה מגיעה אחרונה ודורסת את החדשה. ב-Posts זה קורה כשעוברים מהר בין "כל המסלולים" ל"המסלולים שלי". כל ריצה של ה-effect יוצרת דגל משלה. לפני הריצה הבאה, ה-cleanup מסמן ignore = true לריצה הקודמת, והתשובה שלה לא מגיעה ל-reducer. מכיוון ש-loadPosts מקבל את dispatch כפרמטר, עוטפים אותו ב-safeDispatch שבודק את הדגל.
למה כל בקשה מופיעה פעמיים ב-Network?
בגלל <StrictMode> ב-main.jsx. במצב פיתוח React מריץ כל effect פעמיים, כדי לחשוף effects שלא מנקים אחרי עצמם. בגרסה הסופית (build) זה לא קורה.
מה ההבדל בין PATCH ל-PUT, ולמה בחרתם PATCH?
PUT מחליף את כל האובייקט, וצריך לשלוח את כל השדות. PATCH ממזג רק את השדות שנשלחו. בפרויקט שולחים רק מה שהשתנה, למשל { completed: true }, ולכן PATCH מתאים, וזה גם חוסך בטעויות ובנתונים.
איך עובדת הטעינה בשלבים של התמונות?
json-server תומך ב-_start ו-_limit. בטעינה הראשונה שולחים _start=0&_limit=4. "הצג עוד" שולח _start שווה למספר התמונות שכבר הגיעו מהשרת. ה-reducer מוסיף את התוצאה לסוף הרשימה. אם חזרו פחות מ-4, hasMore הופך ל-false והכפתור נעלם.
מה זה key ולמה הוא חשוב?
מזהה ייחודי לכל פריט ברשימה. בעזרתו React מתאים בין הפריטים ברינדור הקודם לפריטים ברינדור החדש, ושומר את ה-state הנכון לכל אחד (למשל מצב עריכה של ToDoItem). משתמשים ב-id ולא באינדקס, כי אחרי מיון או מחיקה האינדקסים משתנים.
למה הרשימה המסוננת (filtered) לא נשמרת ב-state?
כי אפשר לחשב אותה מ-todos ומ-query. אם היא הייתה נשמרת ב-state, היה צריך לזכור לעדכן אותה בכל הוספה, מחיקה או חיפוש, ובקלות היא הייתה יוצאת מסנכרון. חישוב בכל רינדור תמיד נכון.
איך יודעים אם פוסט או תגובה "שלי"?
משווים String(post.userId) === String(user.id). ההמרה למחרוזת נעשית כי id יכול להגיע כמספר מהשרת או כמחרוזת מהכתובת. בתגובה חדשה נשמרים userId (לזיהוי) ו-name (לתצוגה).
מה קורה לתגובות כשמוחקים פוסט?
json-server מוחק אוטומטית את כל הפריטים שמצביעים על הפוסט דרך postId. באותו אופן, מחיקת אלבום מוחקת את התמונות שלו (albumId). לכן מבקשים מהמשתמש אישור עם window.confirm.
למה נעשה fetch רק במקום אחד (apiClient)?
כדי שכתובת השרת, הכותרות, ה-JSON.stringify, בדיקת res.ok ו-res.json() ייכתבו פעם אחת. כל שירות רק אומר "איזו כתובת ואיזה Method". שינוי (למשל פורט אחר) נעשה במקום אחד.
מה קורה אם נרשמים עם שם שיש בו "/", או עם שם של עמוד קיים כמו login?
שם המשתמש הוא חלק מהכתובת, ולכן ב-Register הוא נבדק מול USERNAME_PATTERN: מתחיל באות באנגלית, ורק אותיות באנגלית, ספרות, . _ -, באורך 3 עד 20. /, ?, #, רווח ו-.. נחסמים. בלי הבדיקה, a/todos היה יוצר לולאת הפניות: Layout קורא מהכתובת username = "a", רואה שזה לא המשתמש המחובר, ומפנה שוב. login מותר ולא מתנגש, כי עמודי המשתמש נמצאים תחת /users/, והכתובת היא /users/login ולא /login.
למה הסיסמה לא נשמרת ב-localStorage?
localStorage פתוח לכל קוד JavaScript שרץ באתר, ואפשר לראות אותו בכלי המפתחים. אין צורך בסיסמה אחרי הכניסה, ולכן מוחקים אותה מהעותק (delete userToSave.password) לפני השמירה.

12מגבלות ידועות (כדאי לדעת לפני שישאלו)

אבטחה בצד לקוח בלבד בדיקת הסיסמה נעשית בדפדפן: השרת מחזיר את המשתמש כולל הסיסמה, והלקוח משווה. גם ההגנה על נתונים של משתמשים אחרים, וגם isMine, קיימות רק בממשק. מי שישלח בקשה ישירה לשרת יוכל לקרוא או למחוק הכול. הסיסמאות שמורות ב-db.json כטקסט גלוי. זו מגבלה של json-server, שהוא שרת לימודי. במערכת אמיתית השרת היה בודק סיסמה מוצפנת (hash) ומחזיר טוקן, ובודק הרשאות בכל בקשה.
אין Cache האתגר האופציונלי של cache לא מומש. כל כניסה לעמוד שולחת בקשת GET מחדש. מימוש אפשרי: לשמור את התשובות באובייקט ב-module (או ב-Context) לפי מפתח כמו "todos-2", להחזיר משם אם קיים, ולעדכן או לנקות אותו בכל POST, PATCH או DELETE.
המשתמש ב-localStorage לא מתעדכן אם הפרטים של המשתמש ישתנו בשרת, העותק ב-localStorage יישאר ישן עד הכניסה הבאה.
